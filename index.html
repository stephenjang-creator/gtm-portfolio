Configured, not rebuilt

Every workflow is the same shape on the same stack, so a new one ships as configuration, not a six-month project. That turns "can we automate X?" into a one-week question: a strategic lever, not a backlog item.

Governed by design

Definitions and thresholds live in one layer RevOps owns. Every output traces to a rule and a source, so it's auditable line by line, and money, comp, and customer decisions stay human-approved by construction.

Adopted, not imposed

Outputs land back in the tools reps and managers already use. The system does the gathering and the first draft; the human keeps the judgment, which is exactly why the reps actually adopt it.

Forecast & pipeline risk · Full-stack + agents LIVE
Intelligent Forecast
An executive-facing forecast the whole leadership team can trust. It reads a bottom-of-funnel pipeline review, applies deterministic rules grounded in MEDDPICC and deal hygiene, and does the two things a forecast call needs: it flags which committed deals are actually at risk, and why, and it projects the number for any timeframe. The deal-by-deal judgment a manager used to do by hand across a 600-deal pipeline, now in seconds, and defensible line by line.
Business outcome Replaces hours of manual deal-by-deal review before every forecast call, and surfaces at-risk commitments a manager skimming the list would miss. Judging each deal against its own region's norm (not one global average) stops EMEA's normally-long proposals from being over-flagged and catches the NA stalls a blanket rule lets through, so managers trust the flags instead of second-guessing them.

The problem it solves

Three executives look at the same forecast and ask different questions: the CFO wants a number defensible to the board, the CRO wants where to point the team, the RevOps VP wants who owns the fix. A black-box model answers none of them credibly. The job is a forecast that's simultaneously prioritized, projectable, and auditable down to the single rule that fired.

How it stays trustworthy

Every flag is owned by a deterministic rule that maps 1:1 to a MEDDPICC or hygiene signal: the model only explains and routes questions, it never sets a flag. So a manager can verify any flag against the CRM in seconds, and the board number holds up because you can point to exactly why each deal is where it is.

Business & process impact
  • Managers review exceptions, not all 600 deals: the first pass is automated; human attention goes where it changes the outcome
  • Region-aware scoring reflects how EMEA and NA actually sell, so the flags earn rep and manager trust instead of getting ignored as noise
  • Every flag is defensible to the board: one auditable rule, built from the deal's own values; no black box on the number the CFO has to stand behind
  • RevOps retunes thresholds in config, with no engineer: the framework adapts as the sales motion changes, so it doesn't decay the quarter after launch
  • Zero external API calls on the deterministic core: no per-deal token cost, and sensitive pipeline data never leaves the building
Tech stack & architecture
Deterministic rule engine Multi-agent layer Python FastAPI React + Vite pandas Model Context Protocol (MCP) Anthropic SDK Docker pytest · ruff · black
Under the hood: engineering rigor & the proof
  • Real evaluation harness: the detector scores itself against labeled ground truth: precision / recall / F1 + confusion, reported per-rule, regenerable with one command. Region-aware scoring lifts it from F1 0.847 → 0.960 (precision 0.74 → 0.92, recall 1.00)
  • Deterministic core makes zero network calls and runs end-to-end with no API key; the LLM paths degrade gracefully when unset
  • Every flag traces to one auditable rule built only from the deal's own values; a manager can verify it against the CRM
  • Period-over-period bookings math (YoY / QoQ / MoM / YTD) and a risk-adjusted projection by timeframe (stage win-rates, haircut on flagged deals, uplift on fast movers)
  • MCP server exposes the detector as read-only tools: structured JSON back, zero LLM calls in any tool
  • All thresholds live in config so a RevOps admin can retune without touching rule logic; all data synthetic

Quota & territory planning · Full-stack + agents LIVE
Territory & Quota Designer
A quota-first capacity planner for the CRO and Head of Sales Ops. It standardizes quota by role from pay, carves each rep's territory backward to support that number, and flags every seller whose book can't generate the pipeline to hit quota, before the plan locks and comp letters go out. It doesn't just diagnose: every gap comes with a one-click fix that recomputes the whole plan.
Business outcome Catches under-covered reps before the year starts, not at the Q3 QBR. On the demo plan (36 reps, a $7M/quarter target, $28M/year) it shows 25 of 36 covered and SMB short $688K of pipeline, then offers three fixes with the tradeoff named: re-tag 102 accounts into SMB, lower SMB's quota, or accept a lower coverage target, plus a safe hiring plan and a cost-of-sale check. Change any assumption and every number recomputes.

The problem it solves

Most orgs set quota by title, from the pay band, not by the size of the book in front of the rep. Nothing guarantees that territory holds enough pipeline to produce the number at the team's real win rates. When it doesn't, the rep is under-covered before day one: attainment slips, cost-of-sale climbs, and the forecast built on those quotas was optimistic from the start. You usually find out at the QBR.

How it inverts the problem

It flips the usual order. Quota is the fixed input, standardized by role and anchored on OTE; the territory is what you build to support it. The carve packs each book to a pipeline-coverage target, and a reverse waterfall proves it against real stage win-rates, so an under-covered rep shows up as an explicit dollar shortfall instead of a number buried in an uneven carve.

Business & process impact
  • Standardizes quota by role, so comp is defensible: same title and segment carry the same number, derived from pay, with no per-rep politics
  • Prices the plan before it locks: total comp, cost-of-sale, and how both move across attainment scenarios, so a quota plan can't quietly break the cost-of-sale model
  • Every recommendation resolves the gap, it doesn't just flag it: the re-tag lever moves real accounts and re-carves until every rep clears, so a planner acts instead of interpreting
  • Spreads a structural shortfall fairly: when a segment can't cover, it raises the worst-covered rep's floor instead of starving one rep to over-fill another
  • Surfaces the gap honestly: when a segment simply lacks the pipeline, it says so and shows where the pipeline actually is, rather than hiding it in the carve
Tech stack & architecture
Deterministic planning engine One-click applyable fixes Python FastAPI pydantic Model Context Protocol (MCP) Vanilla-JS dashboard pytest · ruff · black Render
Under the hood: engineering rigor & the proof
  • Deterministic, tested core: every number the UI shows comes from pure Python in the core engine; 85 unit tests, ruff + black clean, and a fixed seed reproduces the plan exactly
  • Recommendations are computed and returned as an applyable settings delta, with round-trip tests proving each fix clears the issue it targets; the re-tag lever re-carves until every rep clears, not just the segment aggregate
  • Work-back carve vs a naive equal-split under the same quotas: identical total gap ($688K, structural), but the carve lifts the worst-covered rep's floor 2.22× to 2.33× and cuts off-home-region assignments 63.2%
  • Conversion rates resolve rep > segment > global, and the engine records which tier supplied each number, so any waterfall figure carries an audit trail
  • The same engine is an MCP server (15 read-only tools) an agent can drive to interrogate and fix a plan; the model explains and proposes, the deterministic core owns every number. All data synthetic

Deal Desk & contracts · Applied LLMs / RAG LIVE
Deal Desk Helper
The institutional memory a Deal Desk never has time to build. It answers the two questions that stall deals and renewals: "what does this contract actually say about X?" and "which contracts across our book carry clause X?", grounded in citations, so legal and finance can act on the answer instead of re-reading the paper.
Business outcome Turns a multi-hour contract hunt into a cited answer in seconds, and finds obligations that keyword search misses entirely: the "terminate without cause" that never says "termination for convenience." It cites the source clause or declines; it never guesses on language that carries money.

The problem it solves

Contracts rarely use the query's words. "Termination for convenience" shows up as "terminate without cause," "in sole discretion," "without penalty." Keyword search misses them; even a reranker scores them near zero. The system recognizes the legal equivalence and recovers matches pure retrieval scored at zero: the difference between a Deal Desk that finds its own precedents and one that re-litigates every deal.

How it stays trustworthy

Hybrid retrieval → rerank → citation-enforced generation, with a membership-judge step for book-wide queries. Human-in-the-loop by construction: it cites its sources or declines rather than guessing: the only acceptable behavior when the answer sets contractual or financial exposure.

Business & process impact
  • Answers in the deal's timeframe, not next week: a multi-hour, multi-contract review collapses into a cited answer
  • Surfaces clause exposure across the entire book at once: the portfolio-risk question ("who else has this obligation?") no one has time to answer by hand
  • Every answer carries its source citation, so legal and finance act on it without re-reading the contract: trust is built into the output, not assumed
  • Declines rather than guessing when the corpus doesn't support an answer: no confident-but-wrong answers on language that carries money
  • Provenance and licensing handled as a first-class concern: grounded on public, expert-annotated contracts, clean from day one
Tech stack & architecture
Hybrid retrieval + rerank LLM-as-judge eval Python LangGraph ChromaDB Cohere (embed + rerank) Anthropic Claude Streamlit Langfuse tracing CI faithfulness + latency gates
Under the hood: engineering rigor & the proof
  • Evaluation grounded in CUAD's expert annotations (100 real contracts, CC BY 4.0)
  • Faithfulness measured (claim-level), not asserted; declines handled correctly
  • Every stage traced (Langfuse): retrieved chunks, rerank reordering, exact prompt/response, tokens + cost per call
  • SRE metrics from request traffic: p50 21s / p95 60s (single-doc vs. analytical fan-out), 100% citation coverage, 0% failure rate
  • CI fails the build if faithfulness regresses, citation coverage drops below 80%, or p95 latency exceeds 90s
  • Diagnosed a reranker result-cap, a semantic gap, and term polysemy, each with data
  • Zero proprietary data; licensing + provenance handled as a first-class concern

Build-vs-buy & cost · Model evaluation LIVE
Local SLM Evaluation for RevOps
The build-vs-buy decision behind every GTM automation: when confidential CRM and pipeline data can't leave the building, which on-prem model is actually good enough, and what does running it locally save? A reproducible benchmark of three local models on the tasks a GTM assistant really performs.
Business outcome The deliverable isn't a winner: it's a workload-to-model decision framework a team can act on. The headline: the 7B model tied the 3B on quality (87.5% vs 87.6%) while running 2.3× slower. Capacity ≠ quality, so reaching for the biggest model is a measurably wrong, and more expensive, default.

The problem it solves

The most useful GTM automations touch the most sensitive data (named accounts, deal values, comp, churn signals), which often can't be sent to a third-party API at all. Running locally solves confidentiality, per-token cost, and latency at once, but only if the local model is good enough. And small models aren't interchangeable; the differences stay hidden until you measure them against your real tasks.

How it reaches a decision

A Python harness runs 40 prompts across 5 RevOps-relevant categories against each model, three runs each. Objective tasks auto-scored; summarization and safety scored to a published rubric. The output is a table a team can act on: for this workload, deploy this model, with the cost and latency trade named, not hand-waved.

Business & process impact
  • Answers the cost-optimization question directly: a validated local model has a fixed hardware cost and a marginal cost near zero, versus per-token API pricing that compounds across every deal scored and call summarized
  • Keeps confidential pipeline data on hardware you control: nothing leaves the building, which clears the contractual and regulatory limits on sub-processing
  • Replaces "reach for the biggest model" with a defensible framework: the intuitive, expensive default is shown to be measurably wrong on this task mix
  • Names its own limitations (GPU not CPU; ratios generalize but absolutes don't): the discipline that makes an evaluation decision-grade rather than marketing
Tech stack & architecture
Custom benchmark + scoring harness Rubric-normalized scoring Python Ollama Pydantic (constrained gen + validation) GPU-instrumented (RTX 4080, CUDA 12.4)
Under the hood: engineering rigor & the proof
  • Timing taken from the model's native counters: generation speed isolated from load cost
  • Median-of-runs methodology; determinism verified (temp 0 gave byte-identical output across 10 runs)
  • Two-guard reliability pattern: schema-constrained generation + Pydantic validation + single retry, failing gracefully
  • Honest limitations stated up front. GPU not CPU, so speed ratios generalize but absolutes don't
  • Safety scored as calibration (over- vs under-refusal), surfacing small-model over-refusal on benign prompts
